# S01：稳定运行、完整计数与慢域排查

先读同目录 `README.md`、`REPORT_TEMPLATE.md`、S00 报告和原始阶段四交接文档。

## 目标

让一次阶段四测试可判断地成功或失败；复测修复后的 CKPT+HBM；减少个别计算域拖慢整机的情况。

## 边界

只写 `work/S01/`。修改对象的候选副本为 `run_node16.sh` 和 `s4_models.py` 中的同步/计时基础设施；不改模型计算、精度、损失。HBM 分配算法归 S03；发现该层错误时交接证据，避免两边同时修。

## 工作顺序

1. S00 报告明确后，从同一基线建立独立候选。先为运行器写失败场景检查：一个 rank 提前失败、缺少/损坏 JSON、旧结果残留、仅一部分电极/阶段输出、零可用核心。验证这些情况不能获得 PASS。
2. 核查后台进程退出状态、barrier 等待和超时、期望域数与配置一致性。实现最小必要的失败传递和有界等待，确保失败时能收集证据并结束本次作业，不误杀其他任务。
3. 对运行期间的核心负载做有限采样，区分外部占核、内存放置和 HBM 不足。比较现有 SKIP_BUSY 与 36/38 线程等少量方案；不做大规模参数搜索，不把排除最慢域当成修复后整节点。
4. 保持 fp32 与 KML 配置固定，复测：B32+HBM；32 电极 B64+CKPT+HBM；若后一项稳定，补 B32+CKPT+HBM。先单域、后四域、后整节点；资源有限时先四域排除失败再扩大。
5. 每个接受配置至少三轮，逐项给出吞吐合计、最慢域参考值、完整域数、波动和 DDR/HBM 指标。主稳定配置在第二台主机复核。历史 SIGBUS 修复不能仅凭源码存在判为整节点通过。

## 验收

- 失败检查先暴露原脚本问题，再验证候选修复；缺域、退出非零或超时不能 PASS。
- 所有预期 rank 完成，无 SIGBUS/OOM/死等；未解决则写明失败条件，不继续扩大。
- 正确性遵守共同协议；稳定性目标为三轮波动 ≤5%。速度提升不是修复失败处理的必要条件。
- 若慢域仍存在，报告可复现范围和原因置信度；不得无证据归咎于其他用户或硬件。
